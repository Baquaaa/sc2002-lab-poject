1. Overview

Restaurant Rush is a turn-based command-line game in Java. The player is the manager of a restaurant with 2 tables and one Waiter, Chef and Cashier (and a Host in Stage 3). Six customers arrive on turns 1, 4, 7, 10, 13 and 16. Each turn the manager chooses one task for the Waiter (seat, take an order or serve) and which order the Chef cooks. The Cashier, eating, satisfaction loss and walk-outs are automatic. After turn 18 the game is a victory if at least 4 customers have paid, revenue is at least $45 and the average satisfaction of paid customers is at least 60.

The code uses the entity-control-boundary structure taught in the course: rush.entity holds the game objects and rules, rush.control.GameController runs the turn steps, and rush.boundary.ConsoleUI only prints the state and reads input.

Notes on the diagram

  • Inheritance: Customer (abstract) has three subclasses; Staff (abstract) has Host, Waiter, Chef and Cashier; ComboMeal extends MenuItem.
  • Composition: the Restaurant creates and owns its 2 Tables, its Menu and its HappyHour; the Menu owns 3 dishes and 2 combos; the GameController owns the restaurant and the staff.
  • Aggregation: a ComboMeal refers to two existing MenuItems that also exist on their own.
  • Associations: a Customer has 0..1 Order and sits at 0..1 Table; an Order refers to exactly one MenuItem.
  • Enums: CustomerStatus and OrderStatus describe where a customer and an order are in their life cycle.

5. Design considerations

5.1 Key abstractions and responsibilities

ClassResponsibility
GameControllerRuns the 18 turns in the fixed step order, asks the UI for the manager's choices, and checks the victory targets.
ConsoleUIPrints the state and reads input. Rejects input that is not a number in range. Holds no game rules.
RestaurantHolds the tables, queue and customers; seats customers; handles eating, payment records, satisfaction loss and walk-outs; keeps the totals.
Customer (+ subclasses)Satisfaction and status of one customer. Decides what to order, how fast satisfaction drops and the bill discount.
OrderLocked price, cooking progress and status of one order.
Staff (+ Host, Waiter, Chef, Cashier)Each staff member does one task per turn and checks that the task is allowed, throwing InvalidActionException with a reason if not.
Menu, MenuItem, ComboMealThe dishes and combos with price (cents) and preparation units.
HappyHourOnce-per-game activation, turns left, the 20% discount and the recovery amount.

5.2 Design principles in our code

  • Single Responsibility: input/output is only in ConsoleUI; cooking progress is only in Order; payments only in Cashier and Restaurant.recordPayment. When we changed the screen layout no rule class changed.
  • Open-Closed: adding VIP and Critic in Stage 2 meant two new subclasses and one line each in createCustomer; the turn steps were not edited. ComboMeal was added in Stage 3 without changing Order, Chef or Cashier.
  • Liskov Substitution: any Customer subclass can be used wherever a Customer is expected, and a ComboMeal wherever a MenuItem is expected; they keep the same meaning (e.g. a discount never makes the price negative).
  • Interface Segregation and Dependency Inversion: we did not use these. The brief says not to add interfaces just for a checklist, and with one UI and one kind of each object an interface would add files without benefit. See the trade-off below.

5.3 Trade-offs

  • GameController uses the concrete ConsoleUI class. This is simpler, but we cannot swap in a GUI or a fake UI for tests without changing the controller. Instead we test with input scripts piped into the real game (runs/*.txt).
  • Restaurant has quite a few methods. We kept seating, eating and payment records together because they all change the same tables and lists; splitting them would mean passing those lists around.
  • Waiting rules use the CustomerStatus enum instead of a class per state. This keeps the number of classes small; the cost is that status checks are spread over a few methods.
  • Waiter.takeOrder gained a HappyHour parameter in Stage 3. This is a small change to an earlier class but keeps the price calculation in one place.

5.4 Alternative design we considered

We considered a single Customer class with a CustomerType enum and switch statements for loss rate, discount and order choice. It would have fewer classes, but every new customer type would mean editing every switch, and the brief asks for behaviour to be dispatched through the customer objects. We also considered a PricingPolicy interface for Happy Hour; with only one promotion we kept a plain HappyHour class.

5.5 How the player's choices change the result

  • The Waiter can do only one task per turn. On turn 10 of the Stage 2 and 3 runs the manager must choose between serving a READY order and seating a new arrival; whoever waits loses satisfaction.
  • Leaving the Critic in the queue (loses 12 per turn) makes them walk out on turn 12 (Stage 2 and 3 defeat runs).
  • Seating and ordering quickly keeps satisfaction at 90+, so customers upgrade to combos and pay more (Stage 3 victory: $100.30).
  • Starting Happy Hour when customers are waiting helps satisfaction; starting it on turn 1 with one customer wastes it (Stage 3 defeat).

8. Reflections

  • Planning the Customer class as abstract in Stage 1 made Stage 2 easy: VIP and Critic only override methods, and the controller did not change.
  • Making ComboMeal a kind of MenuItem meant the kitchen and payment code worked for combos straight away.
  • Keeping all rules out of ConsoleUI made the game easy to replay from scripts, which we used as our test notes.
  • If we had more time, we would add a UI interface so the controller could be tested without the console, and split Restaurant into smaller classes.
